# D1 파생 색인 (C안)

R2가 정본이고, D1은 R2의 현재 카탈로그에서 언제든 다시 만들 수 있는 가벼운 복사본이다. 검색(본문·표·전체 검색)은 계속 R2가 맡는다. D1은 목록·메타데이터 조회, 통계, 외부 연동, SQL 분석에 쓴다.

## 1. 원칙

1. **원본은 R2**: D1 적재기는 ALIO를 호출하지 않는다. R2 `r2-index/active.json`이 가리키는 검증된 카탈로그와 그 증거 객체만 읽는다.
2. **무료 한도 안에서 하루 한 번에 끝낸다**: 무료 D1은 하루 10만 행 쓰기가 한도이고, 적재기는 8만 행에서 스스로 멈춘다. 전체 재적재를 포함해 한 번에 이 범위 안에 들어오도록 설계한다.
3. **찾아보기 색인(FTS)은 만들지 않는다**: 행 쓰기를 몇 배로 늘리는 FTS5 2글자 색인을 빼고, 기본 키와 꼭 필요한 색인 하나만 둔다.
4. **표는 표 단위로 묶는다**: 표의 각 행을 따로 저장하지 않고, 표 하나를 한 행(JSON)으로 저장한다.
5. **언제든 재생성**: D1을 지우고 다시 만들어도 같은 결과가 나온다. 단위 ID는 결정적으로 만든다.

## 2. 표 구조 (`migrations/0002_derived_index.sql`)

| 표 | 한 행의 의미 | 예상 행 수 |
|---|---|---|
| `regulations` | 규정 1건(ALIO idx = `reg_id`). 이름·옛 이름·폐지 여부·현재 파일·개정일·조문/표/전결 행 수 | 약 213 (폐지 포함 시 증가) |
| `versions` | 지금까지 현재본이었던 첨부 버전 1건(`reg_id` + `file_no`). 지우지 않음 | 약 213부터 개정마다 증가 |
| `units` | 조문 1개 또는 **표 1개 통째**(행은 `rows_json`에 묶음) | 약 1.5만 (추정) |
| `approvals` | 위임전결표의 행 1개(구분·업무·조건·전결권자·검토 필요) | 약 1천~3천 (추정) |
| `sync_state` | 마지막으로 옮긴 R2 카탈로그와 개수 | 1 |
| `sync_usage` | 하루 쓰기 행 수 기록(기존 표 유지, 8만 행 안전한도에 사용) | 실행 수 |

- 모든 표는 `WITHOUT ROWID`이고 보조 색인이 없다. 행 하나를 쓰면 쓰기 1회다.
- 통계는 현재본만 보여 주는 보기(view) `current_units`, `current_approvals`를 쓴다. 예: `SELECT count(*) FROM current_approvals WHERE approver='소장'`.
- 원본은 R2 카탈로그 문서의 `parsed/<document_id>.json` 스냅숏이다. 문서 파싱을 다시 하지 않는다.
- 표 하나가 D1 행 크기 상한에 가까우면 `table_id#1`, `#2`처럼 나눈다.
- 기존 FTS 기반 표(`sections`·`table_rows`·`body_fts`·`table_fts` 등)는 0002에서 삭제한다.

## 3. 적재 흐름 (`scripts/d1/mirror.ts`, GitHub Actions)

1. R2 `active.json`과 카탈로그를 읽는다. 카탈로그 파서 버전이 현재 코드와 다르면 R2 재색인을 기다린다(쓰기 0).
2. `sync_state.catalog_sha`가 같으면 끝낸다(쓰기 0).
3. 규정마다 `document_id`를 비교한다.
   - 같으면: 이름 변경 별칭·폐지 상태 같은 생애주기 필드만 다를 때 `regulations` 한 행을 고친다.
   - 다르면: 새 세대(카탈로그 sha 앞 16자) 행을 `units`·`approvals`에 쓰고, `regulations`의 세대를 바꾼 뒤(전환), 이전 세대 행을 지운다. `versions`에 새 버전을 추가한다.
4. 카탈로그에서 아예 빠진 규정(R2는 폐지 규정도 보관하므로 드묾)은 D1에서도 지운다.
5. 마지막에 `sync_state`를 갱신한다.
6. 하루 8만 행이나 20분에 걸리면 멈춘다. 끝난 규정은 그대로 두고, 다음 실행이 나머지를 이어서 쓴다. 같은 행을 다시 써도 `INSERT OR REPLACE`라 중복되지 않는다.

**실행 시점**: `r2-sync.yml`의 `d1-mirror` 작업이 매시간 R2 동기화 뒤에 실행된다. R2가 바뀌지 않았으면 읽기 두 번으로 끝난다. 마이그레이션은 같은 작업에서 먼저 적용한다.

## 4. 한도 계산

실제 규정 3건(로컬 workerd D1, `npm run test:d1-mirror`) 측정값:

| 작업 | 쓴 행 수 |
|---|---|
| 첫 적재(위임전결규정·여비규정·기술용역 업무규정): 단위 208, 전결 행 827 | 1,042 |
| 규정 1건 개정 | 183 |
| 생애주기만 변경(별칭·누락) | 2 |
| 변경 없음 | 0 |

- 위임전결규정: 기존 방식 약 860행 + FTS 조각 약 3만 개 → 새 방식 단위 36행 + 전결 827행.
- 213건 전체 첫 적재는 규정당 평균 약 70단위로 보면 약 1.5만 단위 + 전결 행 수천 + 쓰기 기록으로 **약 2만 행 안팎**으로 예상한다. 하루 8만 행 안에 들어간다. 실제 값은 운영 첫 적재 후 기록한다.

## 5. 쓰지 않는 것과 한계

- D1 안의 단어 검색은 `instr()`로 전체 단위를 훑는 방식만 가능하다. 무료 한도는 하루 500만 행 읽기이므로 검색 용도로 쓰지 않는다. 검색은 R2 MCP를 쓴다.
- 기존 D1 MCP 서버와 적재기(`src/d1-worker.ts`, `scripts/d1/sync.ts` 등)는 삭제했다. D1 조회·통계 도구가 필요해지면 `current_*` 보기를 읽는 도구로 새로 추가한다.

## 6. 검증 (`npm run test:d1-mirror`, R2 regression CI)

- 0001(기존) → 0002 적용: 기존 표 삭제, `sync_usage` 유지, 새 표·보기 생성
- 옛 파서 카탈로그는 옮기지 않음(재색인 대기)
- 첫 적재: 개수, SQL 통계(소장 전결·검토 필요·부서별 건수), 「8) 공무국외출장」 8행, 부칙 라벨
- 같은 카탈로그 재실행 시 쓰기 0, 규정 1건 개정 시 그 규정만 교체·이전 세대 삭제·버전 이력 2건
- 생애주기만 변경 시 한 행만 수정, 하루 한도로 중단 후 재개 시 중복·잔여 없음, 카탈로그에서 빠진 규정 삭제
